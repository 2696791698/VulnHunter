## 代码审查报告：CodeBadger 内存与 Joern 生命周期

### 审查目标与证据

- 类型：本地工作区静态审查，加运行时只读进程采样。
- 范围：`codebadger/src/services/joern_server_manager.py`、`codebadger/src/tools/core_tools.py`、`codebadger/main.py`、`codebadger/docker-compose.yml`、配置默认值。
- 现场：内层 `codebadger-joern-server` 容器约 4.28 GiB，两个 JVM 的 RSS 各约 2.1–2.2 GiB；CodeBadger Python 服务约 90 MiB。该容器 `HostConfig.Memory=0`，没有 Docker 内存限制。审查末尾开发容器已退出，未重启它，也未执行完整测评或单元测试。

### 🔴 严重问题 1：保留池预算高于容器可用内存

- 当前 `codebadger/.env` 设置 `MAX_ACTIVE_JOERN_SERVERS=8`；`src/defaults.py` 的 JVM 默认参数为 `-Xmx4G -Xms2G`。每个 CPG 对应一个 Joern JVM。`JoernServerManager` 只在新 JVM 到来且池满时按 LRU 淘汰旧 JVM；没有按样例结束或空闲时间自动卸载。8 个 JVM 仅按 `-Xms2G` 就可合计约 16 GiB，超过截图中的 15.3 GiB 开发容器上限。
- `JOERN_MEMORY_LIMIT` 虽进入配置对象，但未见其用于 `docker-compose.yml` 的容器限制或进程启动参数。现场 Docker inspect 确认为 `Memory=0`。`-Xmx4G` 只是单个 JVM 的 Java 堆上限，不是整个 Joern 容器的上限。
- 建议把活跃 JVM 上限与容器预算统一配置，加入空闲淘汰或评测样例完成后的明确释放策略，并对 Joern 容器施加实际的 Docker 内存上限；取值需通过合法 CPG 的峰值测量确定。

### 🔴 严重问题 2：启动或终止失败后可能遗留 JVM

- `joern_server_manager.py:134-137` 启动后台 JVM 后，若 `:147-165` 就绪等待超时，代码只调用 `_cleanup_server()` 清掉端口和客户端登记，没有先确认该 JVM 已终止。`_cleanup_server()` 本身不杀进程。异常分支也如此。
- `terminate_server()` 中发送 `pkill` 后不检查进程是否实际退出；即使 Docker exec 抛异常，仍继续 `_cleanup_server()` 并返回成功。LRU 淘汰调用方也不检查 `terminate_server()` 的返回值。这可能使实际 JVM 存活，而管理器已丢失它的登记，随后再启动新 JVM，真实占用超过池上限。
- 建议在释放登记前按 PID/端口确认目标 JVM 已退出；失败时保持可追踪状态并报告错误。启动失败也应走同一可靠终止路径。

### 🟡 建议修改

- `CPGGenerationQueue.stop()` 仅 `cancel()` worker，未等待退出或处理队列中的任务；`main.py` 的关闭顺序先终止 Joern 服务，再停止构建队列。构建任务里的 `run_in_executor()` 同步 Docker exec 不会因为协程取消而立即停止。建议先阻止新任务、停止并等待构建任务及其容器进程，再关闭 Joern 服务和客户端。
- `core_tools.py:_generate_cpg_async()` 每次创建 `docker.from_env()`，没有在 `finally` 显式 `close()`；这是连接资源生命周期缺口，现场数 GiB 占用的主因仍是 JVM。
- Joern 管理器的 `_ports`、`_lru` 和 `_clients` 没有同步锁；看门狗的重启路径使用 `run_in_executor()`，与其他启动或查询路径可能并发。建议为启动、淘汰、终止引入同一状态锁，并用并发测试验证不超池上限。

### 已有的正常路径

- `remove_cpg(delete_files=False)` 可显式终止某个 Joern JVM并保留磁盘 CPG；LRU 达到上限时会尝试淘汰；`_cleanup_server()` 会关闭被登记的 HTTP 客户端；服务正常关闭时会遍历已登记的 Joern JVM。现有机制有释放入口，但没有可靠覆盖空闲、异常和高并发情况下的内存预算。

### 结论

- `Request Changes`。当前 CodeBadger 的大部分内存是有意保留的 Joern JVM，不是 CodeBadger Python 对象持续泄漏；但保留池大小和失败清理路径会让总内存持续升高，甚至超过开发容器上限。测试未运行，运行时结论限于本次进程采样。
