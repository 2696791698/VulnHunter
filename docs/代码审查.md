### 全量测评 3 并行内存回收复审

#### 现场证据

- Docker Desktop 截图显示外层开发容器约 14.13/15.3 GB。外层 `docker ps` 只显示开发容器，但开发容器内运行了自己的 Docker daemon；内层 `docker ps` 在采样时显示 3 个 `anaconda-container-*` 审计容器和 1 个 Joern 容器。3 个审计容器的 `/workspace` 分别挂载 `eval-1790344118836-1-0083`、`...-0109`、`...-0126` 样例目录。
- 开发容器 `memory.stat` 的 `anon` 曾达到约 11.1 GB，主要是进程内存，不是文件缓存。`python test3.py` 在样例 `...-0083` 的内层容器里从约 4.1 GB 增到超过 7 GB；另观察到 `blow.py`、`mem.py` 等子进程。外层 `memory.events` 的 `oom_kill` 从 0 增至 3。未取到内核日志，不能逐一确认被杀进程，但这些进程与测评审计容器相关，不应归为无关后台任务。
- 内层 `docker inspect` 对 3 个审计容器均显示 `HostConfig.Memory=0`，即没有单容器内存限制。同期桥接进程 RSS 约 0.8 GB，Joern Java 约 2.2–2.8 GB，Pylance 约 1.3–1.5 GB。截图中的陡升主要来自审计容器内部执行的 Python 进程；不是 200 条 `verdict` 记录本身。

#### 🔴 严重：单样例审计容器没有内存限制

- `audit_agent.py` 的 `client.containers.run()` 没有传 `mem_limit`、`memswap_limit` 或相当的资源边界。`web/server/main.py` 的 3 个 worker 只限制同一时刻的样例数，不能限制某个样例在容器内动态验证时占用的内存。
- 现场一个样例容器内的 Python 进程超过 7 GB，触发外层开发容器的 OOM 计数增长。即使样例结束后 `finally` 会移除容器，运行中的内存尖峰仍可能先杀掉其他进程、使样例失败或中断全量测评。建议为审计容器设置与 15.3 GB 总预算匹配的单样例上限，并把触及限制作为明确的样例失败原因记录；之后再用有代表性的合法动态测试确定上限数值。

#### 🔴 严重：Joern 保留池缺少容器级内存预算

- `codebadger/.env` 当前设置 `MAX_ACTIVE_JOERN_SERVERS=8`；`codebadger/src/defaults.py` 的 JVM 默认参数为 `-Xmx4G -Xms2G`。`codebadger/src/services/joern_server_manager.py` 只在池满时按 LRU 停掉旧 JVM，样例完成不会释放相应 Joern 进程。3 个评测 worker 不限制 CodeBadger JVM 数或整个开发容器的内存。
- 单个常驻 JVM 现场已占约 2.2–2.8 GB。在 15.3 GB 容器上，多个 CPG 对应 JVM 加上桥接服务和编辑器进程，存在 OOM 风险；8 个 JVM 的理论堆上限之和为 32 GB，还未计其他内存。建议为 Joern 池设与容器预算匹配的活跃上限和空闲回收，并在全量测评中观测 JVM RSS 与 OOM 事件。

#### 🟡 建议：结果与轨迹的内存保留上限不完整

- `web/server/evaluation.py` 的 `create_run()` 和 `replay_runs()` 只裁剪 `_run_order`，没有删除对应的 `_runs`、`_samples` 与完整 verdict。单次 100 对测评需要保留最多 200 条样例记录，这部分是正常增长；反复运行超过 40 次时，旧记录会一直留在桥接进程内。手动 `drop_run()` 才清理这些对象。
- `web/server/main.py` 在 `span.start` 后立即返回，直到 `span.end`/`span.error` 才按 `MAX_TRACE_BYTES` 淘汰。`agent_tracing.py` 的待发队列按事件条数限制为 8192，但单条载荷无字节上限；默认 384 MB 的轨迹预算因此不是严格的进程峰值上限。3 个并行 agent 的大载荷可以暂时叠加。建议在每次加入 span 时执行预算检查，并为待发队列增加字节预算。
- `audit_agent.py` 每个样例调用 `docker.from_env()`，结束时停止并强制移除容器，但没有显式 `client.close()`；建议在外层 `finally` 关闭 Docker API 客户端。它不是现场数 GB 增长的主要解释。

#### 已确认正常的回收路径

- `audit_agent.run()` 正常退出时尝试停止并移除审计容器；`_run_eval_sample()` 的 `finally` 删除宿主检出目录并清空样例的 checkout 字段。采样时 3 个审计容器仍在运行，说明这些清理路径尚未执行。结果文本与诊断文件保留在磁盘上，属于磁盘占用，不是这次匿名内存增长的主因。

#### 验证边界与结论

- 本轮只做静态代码审查与实时只读进程采样，没有启动新的全量测评，也没有停止现有进程。已经观察到容器 OOM，但未取得所有子进程的完整执行日志，不能断定每个脚本为何被启动。
- 结论：`Request Changes`。这次陡升发生在正在执行的评测审计容器内，直接缺口是没有单样例内存限制；同时 Joern 常驻池过大、旧 run 对象未淘汰及轨迹峰值预算不严。现有结束后清理不能保障运行中不触及容器总内存上限。
